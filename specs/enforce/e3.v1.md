# E3 — Gateway & egress enforcement

Status: **complete and verified against real Envoy** — both transports, mTLS,
opt-in body inspection, egress templates, and a measured p99. Linear milestone
E3 · Gateway & egress enforcement. Locked stack: Envoy + ext_authz gRPC, no
homegrown proxy (technologies.md §2).

## §1 Shape

Three layers, so the transport is swappable without touching enforcement:

1. **`ExtAuthzCore.check()`** — transport-agnostic. Intercepted request
   attributes → canonical Action → `Enforcer` (decide + chain + span) →
   `CheckResult`. The Action: tool = `<scheme>://<host><path>`, verb = HTTP
   method, `origin: gateway`, resource `*` (network layer sees no business
   semantics — that's the SDK's job, E4). `traceparent` is parsed into
   `context.trace_id/span_id`, so gateway verdicts join the caller's trace.
2. **gRPC transport** (`extauthz_grpc.py`) — the locked target. Serves
   `envoy.service.auth.v3.Authorization/Check`.
3. **HTTP transport** (`create_http_service()`) — Envoy `http_service`
   ext_authz server, for environments where a gRPC hop is inconvenient.

Both transports share one decision path, so they cannot disagree about a
verdict.

## §2 Protos: vendored minimal subset, not `xds-protos`

The engine does **not** depend on the `xds-protos` distribution. It ships a
stale copy of `opentelemetry/proto/**` at the *same file paths* as the real
`opentelemetry-proto` package, so whichever installs last wins and
`unified-enforce[otel,gateway]` breaks by install order (observed: the OTLP
exporter died with `cannot import name 'InstrumentationScope'`; uninstalling
xds-protos then deleted opentelemetry-proto's files as collateral).

Instead `protos/ext_authz.proto` declares the fields the engine actually reads
and writes, under our own package name. Protobuf matches on field *numbers* and
tolerates unknown fields, so Envoy's full messages parse against the subset. The
wire service name is set on a gRPC **generic handler**, decoupling it from the
message namespace — so this can coexist with real Envoy protos in one process
without duplicate descriptor-pool symbols.

Field numbers are copied from Envoy v3 and must not drift. The integration
suite is what pins them: it runs real Envoy against the servicer.

## §3 Verdict mapping at the network layer

ALLOW → `OK` + `OkHttpResponse`. DENY → `PERMISSION_DENIED` + HTTP 403.
**DEFER → 403 + `x-unified-verdict: defer`** — fail closed: the gateway has no
interactive approval channel until the approval contract (M0.8) is wired in,
and a deferred network call must not hang an Envoy worker.

Header placement follows Envoy's model, which differs by verdict:

- **Allow** — `x-unified-*` are injected into the **upstream request**
  (provenance: the upstream sees the verdict, rule, and action digest). They
  are *not* on the client's response.
- **Deny** — `x-unified-*` are returned to the **client**, with the body
  `unified-enforce: <verdict>`.

## §4 Principal trust (security-critical)

Identity precedence: **mTLS SAN > header > configured default.**

- `attributes.source.principal` (Envoy sets it from the client cert when
  `include_peer_certificate: true`) is unspoofable and wins. SPIFFE URIs pass
  through verbatim — policy globs match `spiffe://cluster.local/ns/prod/sa/*`
  directly; any rewrite would be lossy guesswork.
- `x-unified-principal` is only as trustworthy as the infrastructure setting
  it. **An agent that can set this header can impersonate any principal.**

  Corrected 2026-08-11: an earlier version of this spec claimed the templates
  defended against that with `request_headers_to_remove`. They did not.
  Route-level header removal is applied when the request is **forwarded** —
  after ext_authz has already decided — so it keeps internal headers off the
  wire to third parties but leaves the engine seeing whatever the agent sent.
  Verified against real Envoy, and now pinned by
  `test_route_level_removal_does_not_protect_the_engine`.

  The real defences, in order:
  1. a **`header_mutation` filter ordered ahead of ext_authz**, which the
     sidecar templates now carry — it deletes the header before the engine
     sees it, so identity can only come from the SAN or the configured default;
  2. `ExtAuthzCore(trust_principal_header=False)`, which refuses the header
     even if one arrives.

  Defence 1 belongs to sidecar deployments. Multi-tenant **gateway**
  deployments convey identity through this header on purpose, so they must
  remove that filter and strip the header at their own trust boundary instead.
- Per-agent **sidecar** deployments should not use the header at all: identity
  is *which sidecar* received the request, so set `default_principal` at
  startup. The header exists for multi-tenant **gateway** mode.

## §5 Envoy templates

`deploy/envoy/ext_authz-grpc.yaml` (preferred), `ext_authz-grpc-mtls.yaml`
(§8), and `ext_authz-http.yaml`: egress sidecar with dynamic forward proxy,
`failure_mode_allow: false` (engine down ⇒ deny), 50 ms auth timeout against a
<10 ms budget, `x-unified-*` allowlisted, principal header stripped. All three
pass `envoy --mode validate` in the integration suite — the mTLS one against a
real certificate chain mounted at the documented path, since Envoy reads cert
files at config load and validating without them would only prove the YAML
parses.

Each carries a commented `with_request_body` block (§9) for operators enabling
body inspection.

## §6 Egress policy — the no-bypass guarantee

`deploy/egress/`: Kubernetes NetworkPolicy, iptables owner-match (VM /
bare-metal / air-gapped), AWS security groups. All encode the same rule: the
agent's only egress destination is the sidecar, plus DNS.

Two traps the templates handle explicitly, because both silently void the
guarantee: **UDP/QUIC** (iptables `REDIRECT` only covers TCP, so an HTTP/3
upgrade would walk straight past the plane — rejected explicitly), and AWS's
**default permissive egress rule** on new security groups. The README's
verification checklist leads with the only test that actually proves
no-bypass: a direct `curl` from inside the agent container must fail to
connect at all.

## §7 Verification

`tests/integration/test_envoy_ext_authz.py` (marked `integration`, excluded
from the default run, skipped without Docker) starts the engine's gRPC server
and a stub upstream, runs **real Envoy** in a container against them, and
asserts:

1. all three shipped templates pass `envoy --mode validate` (the mTLS one
   against a real certificate chain);
2. an allowed request reaches the upstream, which receives the `x-unified-*`
   provenance headers;
3. a denied request is blocked by Envoy with `x-unified-verdict: deny`;
4. an unknown principal is denied;
5. **the body decides the verdict** — same principal, method, and path, with
   only the amount inside the payload differing. This is what pins the vendored
   proto's `raw_body`/`size` field numbers to Envoy's, since Envoy is the only
   thing that populates them;
6. an unreadable body is denied with `source: body_unreadable`;
7. Envoy's TLS client completes a mutual handshake against `ServerTLS` and the
   verdict passes through — interop the unit tests cannot cover, since they use
   grpc's own client on both ends;
8. **killing the engine denies traffic** rather than passing it
   (`failure_mode_allow: false` — the fail-closed guarantee, end to end).

Harness note: the test config uses Envoy's `getaddrinfo` DNS resolver, because
the default c-ares resolver ignores `/etc/hosts` and therefore cannot see
Docker's `host.docker.internal`. Real sidecars address `127.0.0.1` and are
unaffected.

## §8 mTLS between Envoy and the engine

`ServerTLS` (extauthz_grpc.py) supplies transport credentials to the servicer;
`deploy/envoy/ext_authz-grpc-mtls.yaml` is the matching sidecar config. Use it
whenever Envoy and the engine are not the same trust domain — a shared host, a
multi-tenant gateway, any hop off the loopback interface.

The threat is impersonation in both directions, not eavesdropping. Without it
any local process can call the engine directly to map the policy by probing
verdicts, and — the worse direction — any local process that wins the port can
pose **as** the engine and answer ALLOW to everything. `failure_mode_allow:
false` does not help there, because a rogue engine is not a failure.

Two deliberate choices:

- `require_client_auth=True` without a `client_ca` raises at construction.
  gRPC would otherwise accept unauthenticated clients, turning a
  security-critical typo into a silent downgrade.
- The template pins `match_typed_subject_alt_names`, not just `trusted_ca`.
  Verifying only the chain accepts *any* certificate that CA ever issued,
  including one held by a compromised neighbour.

This authenticates the **channel**, not the acting agent: Envoy's client
certificate identifies Envoy. The enforced principal still comes from
`attributes.source.principal` (§4).

Verified in `tests/unit/test_enforce_extauthz_mtls.py` (a client with no cert
and a client with an untrusted-CA cert are both refused) and end to end against
real Envoy's TLS client in the integration suite.

## §9 Request-body inspection (opt-in)

`BodyInspection` on `ExtAuthzCore` parses request bodies into `Action.params`,
so policy can express "no refund over $5,000" rather than only "no POST to
/v1/refunds". Off by default: it changes the latency profile (see §10),
requires Envoy to buffer bodies, and pulls payloads into the audit chain where
the capture level then governs retention.

**Numbers are parsed as strings** (`parse_float=str`). Floats are rejected by
strict canonicalization precisely because their repr is not portable, so
parsing `8000.50` into a float would make the action digest unstable across
verifiers. The literal text is exact and deterministic, and the args matchers
str()-coerce anyway. In CEL: `double(params.amount) > 5000`.

`on_unreadable` governs a body that cannot become params — oversize, truncated,
malformed, a content type outside the allowlist, or JSON that isn't an object.
The default is **deny**: enabling body inspection declares that bodies carry
meaning, so a body we cannot read is a body we cannot clear. That denial is
issued through `Enforcer.record()` rather than returned directly, so it lands
in the audit chain and the trace exactly like a policy verdict, distinguished
by `source: body_unreadable`.

`ignore` is not the unsafe counterpart — it hands the request to the policy
engine with empty params, where a rule whose CEL reads `params.amount` errors
and the existing fail-closed rule denies it as `condition_error`. The modes
differ in *which* layer refuses, not in whether one does.

Truncation deserves its own note. Envoy truncates rather than rejects when
`allow_partial_message: true`, and a prefix of a JSON document can still parse
cleanly by luck — judging a request on a partial payload. The engine compares
Envoy's declared `size` against the bytes received to catch this, but that is a
backstop: the shipped templates set `allow_partial_message: false` so Envoy
rejects oversized requests itself. The HTTP transport cannot detect truncation
at all (Envoy rewrites content-length), so that setting is mandatory there.

## §10 Measured latency (the profiling gate)

`technologies.md` makes this measurement the precondition for any argument that
the data plane needs a Rust/Go rewrite: **measure first, then decide.**

`tests/integration/test_latency.py`, 8 concurrent callers over one shared
channel, 8000 samples per path, on an Apple-silicon laptop:

| path   | p50    | p95    | p99    | max     |
| ------ | ------ | ------ | ------ | ------- |
| `glob` | 2.95ms | 3.34ms | 3.62ms | 4.29ms  |
| `cel`  | 6.63ms | 7.78ms | 8.38ms | 45.00ms |

`glob` is a structural match; `cel` parses a JSON body into params and
evaluates a CEL condition over it — the expensive branch, and the one E4's SDK
will lean on. **Both p99s are inside the 10 ms budget**, so there is currently
no measured case for rewriting the data plane. The `cel` max shows a real tail
worth watching if that path becomes the common one.

Methodology note, because it changed the answer: the load generator runs in a
**separate interpreter**. An in-process client puts load threads and serving
threads on the same GIL, where they measure each other — the first version of
this harness reported a `cel` p99 of 14.85ms that way, nearly double the truth,
and would have argued for a rewrite that the evidence does not support. Envoy
is a separate C++ process, so co-locating the client was measuring an artifact.

What is measured is the engine's serving latency: a full gRPC Check round trip.
Envoy's own filter overhead is excluded deliberately — it is the same whatever
language the servicer is written in, and Envoy reports it in `ext_authz.*`
stats.

## §11 Still open

- Egress templates are verified by inspection and `envoy --mode validate` only;
  a real cluster / VM test is design-partner-deployment work (G2).
- The HTTP template uses `authorization_request.allowed_headers`, which Envoy
  flags as deprecated (config still loads). Revisit when that transport gets
  real use; the gRPC templates are clean.
- DEFER at the gateway remains a 403 (§3), and that is now a decision rather
  than a gap: the approval contract landed in the engine
  (`specs/enforce/approval.v1.md`), but a synchronous HTTP call cannot wait for
  a human without hanging an Envoy worker. Approvals apply to a subsequent
  retry, not to the call in flight.
