## 1. Directory layout

```
~/.unified-ai/
├── discovery/daemons.json
├── mcphub/
│   ├── config.yaml                    # hub-global (transport, audit, approval)
│   ├── dangerous-commands.yaml        # safety floor: patterns that require approval; ships populated, trim to taste
│   ├── workspaces/<name>.yaml         # per-workspace (servers + rules); one active at a time
│   ├── tools/<name>.py                # user-defined built-in tools (auto-discovered)
│   ├── unified-mcp.json               # canonical truth file: hub connection info; derivable into any harness config
│   ├── mcphub.sock                    # Unix socket (mode 0600) — primary transport
│   ├── caller-tokens/<id>.token       # bearer tokens (mode 0600) — TCP fallback only
│   ├── secrets.enc                    # OS-keyring-keyed
│   ├── audit/<UTC-date>.jsonl         # two-phase audit log
│   ├── audit/.lock                    # fcntl exclusive
│   └── logs/mcphub.log                # only when logging redirected; otherwise stdout
└── harness-configs/claude-code.json   # M0 ships ONE harness generator (Claude Code); others = M0.5/M1+
```

All files mode `0600`; all dirs mode `0700`. Hub refuses to start on looser modes.

## 2. Config

### 2.1 Hub-global `config.yaml`

```yaml
listen:
  unix_socket: ~/.unified-ai/mcphub/mcphub.sock     # primary transport
  tcp: 127.0.0.1:7712                                # fallback

audit:
  retention_days: 365

approval:
  enabled: true                                      # master switch; default ON. false = no prompts at all (incl. dangerous floor)

active_workspace: default                            # which workspace to load on start
```

### 2.2 Per-workspace `workspaces/<name>.yaml`

```yaml
# workspaces/work.yaml (for example)
servers:
  github:
    upstream:
      url: https://mcp.github.com
    auth_secret_ref: github-oauth                    # references secrets.enc
  filesystem:
    upstream:
      image: ghcr.io/unified-ai/mcp-filesystem@sha256:<digest>

authz:
  # Default-deny is implicit and not configurable. Anything not matched below is denied.
  rules:
    - tool: "mcp://*/list_*"
      effect: allow
    - tool: "mcp://github/create_issue"
      callers: ["claude-code"]
      effect: prompt
    - tool: "mcp://shell/exec"
      args_filter: { command_starts_with: ["git ", "pytest "] }
      effect: allow
    # Allow-everything (sandbox) posture = a visible catch-all placed LAST:
    # - tool: "mcp://*/*"
    #   effect: allow
```

### 2.3 Workspaces

Inspired by MCP Router's workspace concept and AWS profiles. One workspace active per hub instance. Switch by editing `config.yaml :: active_workspace` and restarting, or via `--workspace <name>` flag at start.

Workspaces let users define context-specific server + rule sets:
- `default` — minimal starter set
- `work` — work credentials + tighter rules
- `personal` — personal credentials + permissive rules
- `sandbox` — `approval.enabled: false` + a trailing catch-all `mcp://*/*: allow` rule for experimentation

`unified-mcphub start` (or `init`) seeds a working `default` workspace — built-ins only, no external servers — with commented examples for adding servers + rules. Edit it in place; copy it to other names for `work` / `personal` / `sandbox`.

**Default-deny is implicit and not configurable** — there is no `default:` field and no `allow_unsafe_default` flag. Anything not matched by an explicit rule is denied. To be permissive, write rules; an allow-everything posture is a visible trailing `mcp://*/*: allow` rule (self-documenting, and the dangerous-commands floor still applies on top of it).

### 2.4 Dangerous-commands safety floor

`~/.unified-ai/mcphub/dangerous-commands.yaml` is a **global** safety floor (applies across all workspaces). Ships populated; the user trims to reduce friction.

```yaml
# Operations that require human approval. Trim to reduce friction.
require_approval:
  - "mcp://*/delete_*"
  - "mcp://*/remove_*"
  - "mcp://*/destroy_*"
  - "mcp://*/drop_*"
  - "mcp://*/force_push*"
  - "mcp://shell/exec:rm -rf*"
  - "mcp://shell/exec:sudo*"
```

Different lifecycle from `authz.rules`: rules you *build up* (start empty, add allows); the danger list ships *full* and you *trim* it. Separate file keeps "stuff I added" distinct from "safety defaults I'm removing." This is a deliberate exception to single-config, justified by lifecycle.

A match forces `effect: prompt` (see §4.2 for precedence + §5 for behavior). Remove a pattern to stop force-prompting that category; `allow_always` on a specific op writes an exact-tool exception.

## 3. Authentication

### 3.1 Transports

| Transport | Mode | Auth |
|---|---|---|
| **Unix socket** at `~/.unified-ai/mcphub/mcphub.sock` (mode `0600`) | Primary | Filesystem permission — only same-OS-user processes can `connect()`. That IS the auth boundary. |
| **TCP** at `127.0.0.1:7712` (loopback only) | Fallback | Bearer token from `~/.unified-ai/mcphub/caller-tokens/<id>.token` (mode `0600`) |

Hub binds both; each harness uses whichever it supports. Refuses to bind non-loopback IP without mTLS (out of M0).

### 3.2 Caller identification

Independent of authentication. Used for audit logging + per-caller rule matching.

- **Unix socket:** harness sends `X-Caller-Id: <name>` header (set by the `install <harness>` command during wiring).
- **TCP:** the bearer token's `caller_token_id` (first 8 hex chars of `sha256(token)`) maps to the caller name; the token file is per-caller.

The `X-Caller-Id` header is **identification, not authentication** — same-user processes are already trusted (the socket permission gates that); the header just tells the hub which harness is calling.

### 3.3 Per-caller bearer tokens (TCP path only)

- Hub mints 32-byte random token; writes to `caller-tokens/<id>.token` (mode `0600`).
- Harness reads file; sends `Authorization: Bearer <token>` on every request.
- `caller_token_id` = first 8 hex chars of `sha256(token)`; logged. Bearer never logged.
- Rotation: regenerate the file via `secrets set <id>-token`.

### 3.4 OAuth flow (upstream MCP services)

- Auth Code + PKCE. Loopback callback at `http://127.0.0.1:7712/oauth/callback`. State + PKCE verifier validated.
- Refresh-token rotation supported.
- CLI: `auth login <server>`, `auth revoke <server>`.

## 4. Authorization

### 4.1 Three states per tool

- `allow` — proceeds, audited.
- `deny` — rejected, audited.
- `prompt` — paused; resolved via §5 approval flow; audited. Requires `approval.enabled: true`.

### 4.2 Rule precedence

1. **Explicit exact-tool rule** in the active workspace (`tool:` with no wildcard, matching the exact tool URI) — wins. This is where `allow_always` / `deny_always` decisions write, so a user can permanently exempt one op from the safety floor.
2. **`dangerous-commands.yaml` pattern match** → forces `effect: prompt` (subject to the §5.1 master switch).
3. **Workspace wildcard rules** in `authz.rules` (first-match-wins).
4. **Implicit default-deny** — anything unmatched is denied. Not configurable (no `default:` field).

Net: dangerous ops prompt by default; an explicit per-op allow overrides the floor for that one op; removing a pattern from the danger file drops the floor for the whole category; allow-everything is a visible trailing `mcp://*/*: allow` rule.

### 4.3 Rule shape

```yaml
- tool: "mcp://github/create_issue"      # URI pattern, * wildcards
  callers: ["claude-code", "opencode"]   # optional; default: any
  args_filter:                           # optional
    command_starts_with: ["git ", "pytest "]
  effect: prompt
  audit_level: standard
```

### 4.4 Tool URI naming (per ADR-0020)

- `mcp://<server>/<tool>` — MCP routed (external server in `servers:` or built-in)
- `mcp://built-in/<tool>` — hub-internal tools (see §10)
- `sdk://<sdk>/<tool>` — SDK-native (M1+)
- `agent://<peer>/<endpoint>` — A2A (M9+)

## 5. Approval flow (opt-in)

### 5.1 Master switch

```yaml
approval:
  enabled: true   # default ON
```

- **`true` (default):** `prompt`-effect calls — whether from `authz.rules` or the `dangerous-commands.yaml` floor — block until the user responds in the in-process TUI. Hub must be foreground (the only mode at M0; see §8).
- **`false`:** kill switch. **No prompts at all, including the dangerous-commands floor.** Everything that would prompt auto-allows with `authz_decision: approval_disabled` recorded in audit. Sandbox / max-speed mode; the user's explicit choice. `allow` / `deny` rules behave normally.

"Approval off means no approval, for anything" — one consistent rule, no per-feature surprises. To keep the dangerous-ops floor, leave approval on and trim `dangerous-commands.yaml` instead.

### 5.2 Mechanism (in-process, no IPC)

```python
# Pseudo:
async def handle_call(req):
    effect = authz.resolve(req)   # applies precedence: exact rule > danger floor > wildcard > default-deny
    if effect == "allow": return await forward(req)
    if effect == "deny":  return error_deny(req)
    # effect == prompt (from a rule OR the dangerous-commands floor)
    if not config.approval.enabled:
        audit.record(req, decision="allow", approval_disabled=True)
        return await forward(req)
    if not hub.is_foreground:                  # background hub: no TUI to approve in
        audit.record(req, decision="deny", reason="no_approval_channel")
        return error_deny(req)                 # FAIL SAFE — never silently run a dangerous op
    decision = await hub.tui.prompt(req)       # blocks; in-process; reads hub's own terminal stdin
    audit.record(req, decision=decision)
    if decision.is_persistent:                 # allow_always / deny_always
        workspace.append_exact_rule(rule_from(req, decision))   # writes a precedence-1 exact-tool rule
    return await forward(req) if decision.allows else error_deny(req)
```

No SSE. No queue. No subscribers. No HTTP decide endpoint — *ever*. The decision comes only from the hub's own terminal, which is what makes it a defense against same-user attackers (they can trigger a prompt but cannot press the key). See ADR-0006 / ADR-0018.

**Background-hub fail-safe:** if a `prompt` fires while the hub runs detached (no TUI), the call is **denied** (audited `no_approval_channel`). To run dangerous ops with a background hub, either trim `dangerous-commands.yaml` or add explicit allow rules.

### 5.3 Decisions

- `allow` — this call only
- `allow_session` — until hub restart (in-memory)
- `allow_always` — appends rule to the active workspace yaml
- `deny` — this call only
- `deny_always` — appends rule

### 5.4 TUI surface

**M0 ships a headless single-keypress prompt** on the hub's own terminal: the
call blocks, the caller/tool/args summary prints, and one keypress
(`a` / `s` / `A` / `d` / `D`) decides. The same-user defense holds — the
decision still comes only from the hub's stdin.

The **full TUI is deferred to M0.5 (SEC-MCP-4)** — a rendered surface with:
- Top: hub status (active workspace, listen sockets, server health)
- Middle: pending prompts (cards with caller, tool, args summary, 5 keyboard actions)
- Bottom: live audit tail

## 6. Audit log

### 6.1 Storage

`~/.unified-ai/mcphub/audit/<UTC-date>.jsonl`, opened with `O_APPEND | O_WRONLY | O_CREAT`. Single-writer; `.lock` fcntl exclusive at startup. Daily rotation at UTC midnight. Default retention 1 year.

### 6.2 Two-phase entries

Per call: `received` (before forwarding) + `completed` (on resolve), paired by `request_id`. `deny` writes `received` only.

**`received`** fields: `request_id`, `trace_id`, `span_id`, `ts`, `seq`, `caller_id`, `caller_token_id`, `mcp_server`, `tool`, `args`, `args_size_bytes`, `authz_decision`, `authz_rule`, `audit_level`.

**`completed`** fields: `request_id`, `ts`, `seq`, `duration_ms`, `result`, `result_status`, `result_size_bytes`, `prompt_response_ms`, `upstream_request_id`, `redactions_applied`.

`authz_decision`: `allow | deny | prompt_allowed | prompt_denied | approval_disabled`.

### 6.3 Audit levels

- `minimal` — `args`/`result` `null`
- `standard` *(default)* — captured; response-scrubber redacts known secret shapes
- `detailed` — captured raw
- `full` — same as `detailed` at M0. (The originally-planned 4KB stdout tail is N/A for routed MCP calls — there is no per-call stdout stream; it returns if/when the hub spawns process-tools whose stdout it owns.)

### 6.4 Durability

Sync `os.write` append (~50µs) into the OS page cache — immediately readable and surviving a process crash. `fsync()` on daily rotation and on graceful shutdown; no periodic fsync thread (power-loss durability beyond that is out of scope per ADR-0009, which doesn't defend against attackers/events at that level). Write errors → call fails with `error.code = "audit_error"`.

### 6.5 CLI

`audit show | pair | search | tail | lint | prune`.

## 7. Sandboxing defaults

> **Deferred to M0.5 (SEC-MCP-5).** M0 runs MCP servers as local **processes**
> (`command:` stdio) or reaches them over **HTTP** (`url:`) — **no Docker
> dependency**, consistent with the §15 same-user trust boundary. `image:`
> (container) upstreams are rejected until M0.5.

*How* a server is launched and *how* it is sandboxed are separate axes. The
launch backend is chosen per-server (`command:` process | `url:` http | `image:`
container). Sandboxing (M0.5) is an enforcement policy applied to whichever
backend runs the server — neither approach is privileged:

- **Container backend** → rootless container (uid 10001), readonly rootfs,
  `--network=none` by default, all capabilities dropped + seccomp, image-digest
  pinning required (no tag-only; `verify: false` opts out with a loud warning),
  Sigstore verification for `ghcr.io/unified-ai/*`. Per-OS: Linux → rootless
  Podman else Docker; macOS → Docker Desktop or Colima; Windows → Docker Desktop.
- **Process backend** → OS-level sandbox (macOS `sandbox-exec`, Linux
  bubblewrap / landlock + seccomp) — a sandboxed runtime process with no Docker
  dependency.

Default at M0/M0.5 stays the unsandboxed local process; sandboxing is opt-in.

## 8. Hub lifecycle (foreground only)

M0 ships foreground only — no daemon mode, no service install.

- `unified-mcphub start [--workspace <name>]` — runs in foreground; renders TUI if `approval.enabled: true`, else plain logging to stdout.
- ctrl-C / SIGTERM: graceful drain (10s), flush audit, release locks, exit.
- Crash recovery: child MCP server crash → exponential backoff (1, 2, 4, 8, 16, 32, 60s capped). 5 crashes in <60s uptime each → mark unhealthy.
- File-watch reload: watcher on `config.yaml` + active `workspaces/<active>.yaml`. On change: re-validate; failure → log loud + keep prior config. Success → server diff applied.

**Backgrounding** is the user's choice via standard Unix tools:
```bash
tmux new -d -s mcphub 'unified-mcphub start'
# or
nohup unified-mcphub start > ~/.unified-ai/mcphub/logs/mcphub.log 2>&1 &
```

No systemd unit, no launchd plist, no Windows service. (May add at M0.5+ if real demand surfaces.)

## 10. Built-in tools

The hub IS an MCP server. Its tool list aggregates:

1. **External MCP servers** from active workspace's `servers:` — proxied via the `unified-mcp-client` package (async; stdio + streamable-HTTP; built on the official `mcp` SDK). See [ADR-0023](../../docs/adrs/0023-mcp-client-shared-package.md).
2. **Hub-native + user built-ins** registered via a hub-local `@tool` decorator (see §10.1). When the optional `unified-ai-orchestrator` is installed, its `UnifiedToolRegistry` tools bridge in too — an optional integration, never a hard dependency.
3. **User-defined tools** in `~/.unified-ai/mcphub/tools/*.py` (auto-discovered at startup; file-watched).

All surface as `mcp://<source>/<tool>`. Built-ins use `mcp://built-in/<tool>`. The interchange type is `mcp.types.Tool` (no parallel tool model); richer tool models project to/from it at their boundaries (ADR-0023).

### 10.1 User tool module shape

```python
# ~/.unified-ai/mcphub/tools/my_tool.py
from unified_mcphub.tools import tool   # hub-local decorator; emits an mcp.types.Tool

@tool(name="my_tool", description="Does the thing")
def my_tool(arg1: str, arg2: int = 5) -> str:
    return f"did the thing: {arg1} x {arg2}"
```

Subject to the same authz rules as any other tool.

## 11. Harness wiring

### 11.1 Canonical truth file

Hub generates `~/.unified-ai/mcphub/unified-mcp.json` on start and any config change:

```json
{
  "name": "unified-hub",
  "transports": {
    "unix_socket": {
      "path": "/Users/<user>/.unified-ai/mcphub/mcphub.sock",
      "preferred": true
    },
    "tcp": {
      "url": "http://127.0.0.1:7712/mcp",
      "auth": {
        "type": "bearer-token-file",
        "path": "/Users/<user>/.unified-ai/mcphub/caller-tokens/<caller-id>.token"
      }
    }
  },
  "active_workspace": "default"
}
```

Single source of truth. Docs reference this file when explaining wiring for any harness.

### 11.2 Single install command

```
unified-mcphub install <harness>                  # install for one harness
unified-mcphub install <harness> --dry-run        # show what would happen
unified-mcphub install --list                     # list supported harnesses
unified-mcphub uninstall <harness>                # reverse
```

Per-harness logic lives in `packages/mcphub/src/installers/<harness>.py`. Each installer is small (~10–30 lines) and follows this preference order:

1. **Use the harness's own MCP-registration CLI** if available (e.g., `claude mcp add ...` for Claude Code, `opencode mcp add ...` for OpenCode if it exists).
2. **Fallback: merge into the harness's MCP config file** (JSON/TOML/etc.) with timestamped backup at `<config>.backup-<UTC-ts>`.
3. **Fallback: print snippet for manual copy-paste**.

Optional `--append-instructions <path>` flag appends an "MCP hub guidance" section to a project instructions file (CLAUDE.md, etc.) — additive, doesn't replace the MCP config step.

### 11.3 M0 ships two installers: Claude Code + OpenCode

M0 ships `install_claude_code` and `install_opencode`. Each uses its harness's own MCP-registration CLI if available (`claude mcp add ...`, `opencode mcp add ...` or equivalent), falling back to config-file merge with backup.

Other harnesses (Codex / Antigravity / OpenClaw / Aider / Cline / Continue) ship as separate small installer functions in M0.75 / M1 / M2 as demand surfaces. Until then, they're doc-driven manual wiring via `docs/harnesses/<harness>.md` (referencing `~/.unified-ai/mcphub/unified-mcp.json`).

Documented manual install at `docs/install/windows.md`.

`received` + `completed` entries in `~/.unified-ai/mcphub/audit/<today>.jsonl`, paired by `request_id`.

## 15. Endpoint security

| Endpoint | Auth | CSRF |
|---|---|---|
| `POST /mcp/<server>/...` | Unix socket filesystem perm OR TCP bearer | n/a |
| `GET /oauth/callback` | `state` + PKCE verifier | per OAuth |
| `GET /status` | Loopback-only | n/a |

That's it — no `/v1/prompts/*`, no `/approve` SPA at M0. Prompts are entirely in-process via the TUI.

**Hardenings:**
- Unix socket: filesystem perms (0600) — only same OS user can connect.
- TCP: loopback-only; refuses non-loopback bind without mTLS.
- Token files: 0600 enforced at startup; refuse otherwise.
- OAuth: state validation + PKCE; single-use state.

**Not defenses:** process-level isolation from same-user attackers, root attackers, kernel compromise, network attacks.
